# Hallucination Prevention — Entity Gate for Narration Write-Back

**Date:** 2026-05-09
**Status:** Design complete, awaiting user review
**Follows:** [2026-05-04 LLM context engine fixes](../plans/2026-05-04-llm-context-engine-fixes.md) (deferred item: "Generic-item / minor-NPC hallucination — needs Zero-Dummy reinforcement plus a post-generation entity validator")

## Problem

Narration generated by the LLM occasionally invents entities — places ("Toprak Village"), incidental NPCs ("Marta the herbalist"), establishments ("Mira's General Store"), and items. The two write-back paths in the world-building service then faithfully record these fabrications:

- `lore-extractor.js` writes `campaign_world_lore` rows whose `subsection` is the fabricated entity name. The lore is then loaded into the next prompt's `## World Lore` section, reinforcing the hallucination across calls until the loop self-perpetuates. The 2026-05-04 Test1 incident left 20 polluted lore rows that had to be purged manually.
- `npc-extractor.js` writes `npcs` rows for incidental named characters. Its existing dedup is name-based, so fresh fabricated names always look new and get persisted. Test1 accumulated 23 hallucinated NPC rows ("Marta", "Kael", "Old Woman" across 8 burgs).

The 2026-05-04 work tightened the *narration-side* prompts so the LLM stops carrying prior chat names forward, but did nothing to the extraction side. As long as a single narration ever names a fabricated entity, it ends up in the DB.

## Goal

Prevent fabricated entities from being persisted to `campaign_world_lore` or `npcs`, while leaving the narration text itself untouched. The chat may occasionally still mention an unnamed tavern or fictional shop — that's accepted creative latitude. The hard line is at the DB write.

A secondary goal: reduce how often the LLM fabricates in the first place by giving extractors a positive list of known entities to anchor against (Zero-Dummy reinforcement).

## Non-goals

- **No retroactive cleanup.** Existing polluted rows in any campaign stay. A future plan can ship a CLI cleanup tool; the resolver built here would power it.
- **No new entity tables.** A `public.npc_shops` table already exists and is consumed by the resolver (see Components below). What stays out of scope is *promoting* unnamed narration mentions ("an inn", "a clay jug") to canonical entities — that's the deferred culture-aware naming work's territory.
- **No regeneration of bad narrations.** A two-pass LLM judge (generate → validate → regenerate) was considered and rejected as too expensive for the marginal player-experience gain.
- **No schema migration.** The gate is purely in extractor logic; no new columns on `campaign_world_lore` or `npcs`.
- **No changes to `LLMContextManager`.** Narration-side context stays as shipped on 2026-05-04. This work feeds the *extraction* side, which previously had no world awareness.

## Architecture

One new module, three edits, no schema change.

```
server/services/world-building/
├─ entity-resolver.js          NEW   — case-insensitive lookup over the world's named entities
├─ lore-extractor.js           EDIT  — uses resolver; receives Known entities in user prompt
└─ npc-extractor.js            EDIT  — uses resolver to build entity index for prompt

server/services/narration/
└─ proactive-narrator.js       EDIT  — extends Zero-Dummy clauses to places/items/shops

tests/world-building/                NEW directory
├─ entity-resolver.test.js
├─ lore-extractor-gate.test.js
└─ npc-extractor-prompt.test.js

tests/llm/proactive-narrator-prompts.test.js   EDIT  — assert new clause
```

The resolver is the single source of truth for "does this name exist in this campaign's world?". It's a stateless service that takes `(campaignId, name, kinds[])` and returns either `{ kind, id, canonicalName }` or `null`. Both extractors call it. The lore-extractor *also* calls a bulk variant (`buildEntityIndex`) up-front to construct the entity index it injects into the LLM prompt.

The boundary is deliberate: `LLMContextManager` is for *narration generation* (it builds the prompt sent to the DM model). The new resolver is for *post-narration extraction* (gating what gets written back to the DB). They share lookup tables (`maps_burgs`, `npcs`, `locations`) but serve opposite directions of data flow.

## Components

### 1. `entity-resolver.js` (new)

Two exported functions.

**`resolveEntity({ campaignId, name, kinds })`** — single lookup.

- `name`: a string. Normalised by lowercasing, collapsing internal whitespace, and stripping non-alphanumeric punctuation (same shape as the existing `normaliseName` in `npc-extractor.js:113`).
- `kinds`: array of `'burg' | 'state' | 'region' | 'npc' | 'location' | 'shop'`. The resolver searches kinds in argument order; the first hit wins. This lets callers control precedence (e.g. lore-extractor passes `['burg','state','region','npc','location','shop']`, NPC paths pass `['npc']` only). The `'shop'` kind resolves against `public.npc_shops` (which already exists; `geographic-context-builder.js:238` queries it).
- Returns `{ kind, id, canonicalName }` or `null`.
- **Exact normalised match only.** No fuzzy matching, no Levenshtein, no substring containment. Reason: "Toprak Village" must NOT silently resolve to one of the 15 real "Toprak" burgs — that would reintroduce the hallucination loop through a softer back door.
- **Campaign-wide scope, not radius-limited.** Reason: lore extraction is asynchronous (fire-and-forget from `dm-narrator.js:128-155`); a fact about an NPC the party met an hour ago shouldn't be rejected because the player has since wandered.

**`buildEntityIndex({ campaignId, scope })`** — bulk fetch for prompt injection.

- `scope`: `{ insideBurgId?, locX?, locY? }`. No radius parameter — the implementation matches the existing geographic-context patterns: k-nearest for burgs (`MAX_NEARBY_BURGS = 8`, ordered by `ST_Distance`), `linked_burg_id`-scoped for NPCs and shops, campaign-scoped for everything else.
- Returns a structured object:

  ```js
  {
    burgs:     [{ id, name, statefull }, …],   // current + ≤8 nearest by ST_Distance
    states:    [{ id, name }],                  // distinct statefull values across the burgs above
    regions:   [{ id, name }],                  // campaign_regions whose geom contains the player point
    npcs:      [{ id, name }],                  // npcs linked_burg_id IN (currentBurg, ...nearbyBurgs)
    locations: [{ id, name }],                  // discovered locations only (is_discovered = true)
    shops:     [{ id, name }],                  // npc_shops where npc.linked_burg_id IN scope
  }
  ```

- **Scope-limited** (unlike `resolveEntity`) because this populates the LLM prompt and prompt size matters. The k-nearest pattern matches `geographic-context-builder.js:120` so the lore extractor sees the same scope the narration LLM saw.
- **No caching.** Worst case is six indexed lookups per extraction — a few ms. Cache invalidation would be the third busting layer in this codebase and isn't worth the savings.

### 2. `lore-extractor.js` (edit)

`extractAndPersistLore` becomes a three-step pipeline.

**Step 1: Build the entity index.** Before the LLM call, invoke `buildEntityIndex({ campaignId, scope: { insideBurgId, locX, locY } })`. The function's existing `_locX/_locY/_insideBurgId` parameters (currently underscore-prefixed and ignored at `lore-extractor.js:68-70`) finally get used.

**Step 2: Inject `## Known entities` into the user prompt.** The new prompt shape:

```
## Known entities (extract facts ONLY about these — do not invent new places, NPCs, or establishments)

Settlements: Folive, Toprak, Yelensaz, Karaman, …
States: Sultantorut, Kürehan
Regions: The Bone Marches
NPCs: Sorceff, Asmodeus, Karam the shepherd, …
Locations: The Old Well
Shops: Mira's General Store, …

## Narration to analyse
{narrationContent}
```

Plus an addition to `EXTRACT_SYSTEM_PROMPT` (a Zero-Dummy clause): *"If a fact's `subsection` is not in the Known entities list, DROP it. Do not invent shops, taverns, items, or named places. If the narration uses a name that isn't in the list, treat it as descriptive prose and skip the fact."*

**Step 3: Post-LLM resolver gate.** After parsing the LLM's `facts` array, run each fact's `subsection` through `resolveEntity({ campaignId, name: fact.subsection, kinds: ['burg','state','region','npc','location','shop'] })`. Drop unresolved facts with a `logInfo('Lore extractor: dropped unresolved subsection', { campaignId, subsection, contentPreview: content.slice(0,80) })` line. Resolved facts proceed to `INSERT INTO campaign_world_lore` exactly as today — no new columns, no schema change.

### 3. `npc-extractor.js` (edit)

Two changes.

**Inject the entity index into the user prompt.** Same Known entities block as the lore extractor. A new line in `EXTRACT_SYSTEM_PROMPT`: *"If the narration anchors an NPC to a place not in Known settlements (e.g. names a village, tavern, or shop that isn't listed), do NOT extract that NPC — they're tied to a fabricated location."*

**No post-LLM resolver call for the NPC itself.** New NPCs are by definition not yet in `npcs`, so resolving them would always fail. The prompt-side push is the only gate for the NPC extractor; the existing post-LLM validation (`isDuplicateNpc`, age caps, PC-name reject) stays unchanged.

The asymmetry with lore (lore gets a hard post-LLM gate, NPCs get only the prompt-side push) is intentional: an NPC's *anchor place* is textual context buried inside `narrationContent`, not a structured field. Detecting it post-LLM would require a regex pass over prose looking for fabricated place names — brittle. The prompt-side push is the better lever.

### 4. `proactive-narrator.js` (edit)

Add one line to each of `AREA_DESCRIPTION_SYSTEM_PROMPT` and `WORLD_TURN_SYSTEM_PROMPT`, in the same terse style as the existing 8-line prompts:

> *"Do not invent named establishments, shops, taverns, items, or settlements. Refer to commerce, lodging, and goods generically ('a market stall', 'an inn', 'a clay jug') unless a specific name appears in the geographic or NPC context above."*

The clause is intentionally weaker than the anti-priors clause: "a tavern" without a name is allowed. Players never seeing tavern names is a worse experience than the occasional fabricated tavern; the gate stops fabrications from compounding into lore, but the prose can stay coloured.

## Data Flow

End-to-end for a single narration:

1. Narration LLM call runs as today via `proactive-narrator.js` (now with the slightly stronger Zero-Dummy clause). Output is posted to chat by `dm-narrator.postNarration`.
2. `dm-narrator.js:131-154` fires lore + NPC extractors in parallel, fire-and-forget.
3. **Lore path:**
   - `buildEntityIndex({ campaignId, scope })` runs five indexed queries in parallel.
   - User prompt assembled with `## Known entities` block prepended to `## Narration to analyse`.
   - Lore-extraction LLM call runs.
   - Each parsed fact's `subsection` is passed through `resolveEntity`. Unresolved → dropped + log line. Resolved → `INSERT INTO campaign_world_lore`.
4. **NPC path:**
   - `buildEntityIndex` runs (same scope; ideally we'd share the result with the lore path but the two extractors run in parallel and independent — duplicate query is fine, it's ~5ms).
   - User prompt now includes `## Known entities` (in addition to the existing `## Existing NPCs at This Location` block).
   - NPC-extraction LLM call runs.
   - Existing post-LLM validation (dedup, age caps, PC-reject) gates writes.

## Error Handling

Three failure modes, three responses. None blocks narration.

**1. Resolver query fails (DB hiccup).** `resolveEntity` and `buildEntityIndex` catch and log, returning `null` / empty index respectively. Lore extraction then falls back to the *current* permissive behaviour — every fact is written, no gate. Reason: a DB failure on the resolver shouldn't silently suppress all extraction; degraded-mode pollution is recoverable, lost extraction is not.

**2. Entity index is empty (new campaign with nothing in scope, or wilderness).** The LLM gets `Known entities: (none)` in its prompt; the system clause tells it to skip facts whose subsection isn't listed; post-LLM resolution drops everything. Net effect: a fresh wilderness narration writes no lore. Correct behaviour — there's nothing real to anchor to, so any extracted fact would be a fabrication by definition.

**3. LLM ignores the Known entities rule.** Post-LLM `resolveEntity` catches it and drops the fact. Logged at `logInfo` (not error — it's expected), with `{ campaignId, subsection, contentPreview }`. No alert/metric in this plan; if it fires constantly we'll see it in logs and tune the prompt.

The fire-and-forget pattern in `dm-narrator.js:128-155` is preserved — extraction failures don't block chat.

## Testing

Real-DB Jest integration tests, matching `tests/llm/context-manager.test.js` from the 2026-05-04 work. Three new test files; all reuse `tests/fixtures/llm-context-fixtures.js` (`createTestCampaignWithTwoPlayers`).

**`tests/world-building/entity-resolver.test.js`** — pure unit tests against the resolver.
- Resolves an existing burg by exact name → returns `{kind:'burg', id, canonicalName}`.
- Resolves with case/whitespace variation ("yelensaz", "  Yelensaz  ") → same result.
- Rejects fuzzy match (input "Toprak Village" with real "Toprak" burgs nearby) → returns `null`.
- Resolves an NPC scoped to campaign, not by location.
- Resolves an `npc_shops` row when `'shop'` is in the kinds list.
- `kinds` ordering controls precedence (e.g. an NPC and a shop share a name; the kind passed first wins).
- `buildEntityIndex` returns nearby burgs only (k-nearest, not the whole world).
- `buildEntityIndex` excludes undiscovered locations.
- DB failure → returns `null` / empty index, doesn't throw.

**`tests/world-building/lore-extractor-gate.test.js`** — exercises the post-LLM gate. Uses a stub `llmService` that returns a canned response (one resolvable fact + one fabricated `subsection`).
- Resolvable fact persists; fabricated fact is dropped.
- Empty Known entities scope → all facts dropped.
- Resolver returns `null` (DB failure simulation) → falls back to permissive behaviour, all facts persist.
- Verify the `## Known entities` block appears in the user prompt the stub LLM receives.

**`tests/world-building/npc-extractor-prompt.test.js`** — verifies the prompt changes only.
- Stub `llmService` captures the user prompt; assert `## Known entities` appears with the expected burgs/states.
- Assert the new system-prompt clause about fabricated places is present.

**Extend `tests/llm/proactive-narrator-prompts.test.js`** — one new assertion per system prompt: each contains the new "do not invent named establishments" line.

**Browser verification** — same loop as the 2026-05-04 plan. Take a clean campaign, narrate area entry in a real burg, then trigger world-turn narration. Confirm `campaign_world_lore` rows have only resolvable subsections; confirm chat narration still reads naturally despite the new clause.

`npx tsc --noEmit` and `npx jest tests/world-building tests/llm` are the green-bar gates before commit.

## Out of scope (intentionally deferred)

- **CLI cleanup tool** for retroactive purging of polluted lore/npcs in existing campaigns. Same resolver would power it; track as a follow-up.
- **`resolved_kind`/`resolved_id` columns on `campaign_world_lore`.** Useful for joining lore to its anchor entity, but no current consumer; revisit when one appears.
- **Items/shops as canonical entities.** Belongs to the deferred culture-aware naming layer (memory: `project_culture_aware_naming.md`).
- **Two-pass LLM judge** (generate → validate → regenerate). Considered and rejected as too expensive.
- **Hallucination metric / dashboard.** Log-grep is sufficient for this plan; if drop rates trend wrong, escalate to a metric in a follow-up.
